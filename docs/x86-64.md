# x86-64: running the kernel natively on PCs (design, for review)

Status: a proposal; nothing here is implemented. Two pieces are being built in parallel and
this design assumes them: `coolc --target x86_64` (a port of Aiwnios's `x86_64_backend.c`),
and QEMU `-M virt` support on arm64 (GIC, PL011, PSCI chosen from the FDT), which is the first
step away from "one platform, hard-wired". Choices that are yours are listed with options
and a recommendation (**Rec.**) and collected at the end.

The goal: the same kernel sources, shell, compiler, Warm and tools run on an x86-64 PC or VM
(QEMU TCG on the Mac, QEMU/KVM on Linux, later real PCs), including the parts that make the
system what it is: the compiler and `MakeKernel` inside the OS, byte-for-byte reproducible.

## 1. Boot protocol

What the kernel needs from its loader: 64-bit long mode (or a way to get there), the memory
map, the ACPI root pointer (RSDP), the command line, and on real machines a framebuffer.

- **A. Multiboot2** (GRUB). Enters in 32-bit protected mode with a tag list (memory map,
  RSDP, framebuffer). QEMU's `-kernel` does not load Multiboot2 (only Multiboot1, which
  lacks RSDP and 64-bit fields), so development would need a GRUB disk image.
- **B. UEFI.** The kernel (or a small loader) is a PE/COFF `BOOTX64.EFI` on a FAT ESP. It
  gets the memory map, RSDP and the GOP framebuffer from firmware and calls
  `ExitBootServices`. The standard on every current PC, and QEMU runs it with OVMF. The
  repository already builds UEFI binaries (`boot/uefi-probe`, clang + lld-link).
- **C. The Linux boot protocol** (bzImage, `qemu -kernel`). QEMU starts it in 16-bit real
  mode in the setup code, so we would write real-mode setup code to reach long mode. Its
  64-bit entry is only used by loaders that support it (not QEMU's direct boot).
- **D. PVH** (an ELF note `XEN_ELFNOTE_PHYS32_ENTRY`), which QEMU's `-kernel`, QEMU `microvm`,
  Firecracker and cloud-hypervisor load directly. Entry is 32-bit protected mode, paging
  off, with `hvm_start_info` (memory map, RSDP, command line). No firmware, fast to boot:
  the equivalent of coolvm loading `kernel.Image`.

**Rec.: D, then B.** PVH is the development and test path (`qemu -kernel build/x86/kernel.elf`,
milestones 1-3), and a UEFI loader is added for the screen milestone and real PCs. Both are
thin entry stubs: each builds the same `CBootInfo` (memory ranges, RSDP, command line,
optional framebuffer) and jumps to the same 64-bit entry, so everything after the stub is
shared. Multiboot2 is not needed if UEFI is there; C costs real-mode code for no benefit
over D.

The PVH stub (`BootX64.S`): in 32-bit mode, build identity-mapped page tables (2 MiB pages
over the memory map, later refined by the kernel), load a GDT, set `CR4.PAE`, `EFER.LME`
and `EFER.NXE`, enable paging, far-jump to 64-bit code, set the stack, apply the module
relocation table (as `Boot.S` does on arm64 when m1n1 loads the Image elsewhere), and call
`KMain(image_end, boot_info)`.

## 2. Hardware discovery

On arm64 `FdtInit` walks the device tree and fills globals (`fdt_uart`, `fdt_cpu[]`, the
virtio-mmio nodes, the framebuffer, the finisher, the clock), which drivers read. Proposal:
make that set of globals an explicit **platform description** (`CPlat plat`, in a new
`Plat.cool`) that is filled by either `FdtInit` (arm64) or `AcpiInit` + `PciScan` (x86), and
have drivers select on it: CPUs (hardware ids), the interrupt controller kind and address,
the serial port (kind: Apple UART, PL011, 16550; MMIO address or I/O port; IRQ), the timer,
memory ranges, the framebuffer (address, size, stride, format), virtio devices (each with
its transport: MMIO base, or PCI function), the power-off/reset method, and the boot-time
clock. The arm64 QEMU `virt` work does the arm half of this refactor already (GIC vs AIC,
PL011 vs Apple UART chosen from the FDT); x86 adds one more source.

ACPI, the subset we parse (tables only):

| Table | What for |
|---|---|
| RSDP → XSDT | the table list |
| MADT | LAPIC ids (the CPUs), I/O APIC address and GSI base, interrupt source overrides (e.g. ISA IRQ 4 for COM1) |
| MCFG | the PCIe ECAM base, for PCI configuration access |
| FADT | the reset register, PM1a control (power-off), the century register of the RTC |
| HPET | only if calibration needs it (see the timer) |

Power-off needs the `\_S5` sleep type from the DSDT, which is AML. Options: (a) no AML
interpreter: find the `_S5_` package in the DSDT bytes (a well-known scan that works on
QEMU and most firmware); (b) an AML interpreter (e.g. a c2hc port of `lai`, thousands of
lines). **Rec.: (a)**, plus QEMU's `isa-debug-exit` device for test exit codes (like coolvm's
finisher).

PCI: walk buses through ECAM (MCFG), falling back to the `0xCF8`/`0xCFC` ports. Only what is
needed: find functions by vendor/device (virtio is vendor `0x1AF4`), read BARs, enable
memory and bus mastering, walk the capability list.

## 3. The arch split

Arch-neutral HolyC stays as it is; what moves behind an arch boundary:

| Area | arm64 (today) | x86-64 |
|---|---|---|
| Entry, relocation | `Boot.S` (Linux Image header) | `BootX64.S` (PVH note; UEFI loader later) |
| Primitives | `Arch.S`: IRQ on/off, WFI/WFE/SEV, atomics, barriers, TLB and I-cache, setjmp | `ArchX64.S`: `cli`/`sti`, `hlt`/`pause`, `lock cmpxchg`/`xadd`, `mfence`, `invlpg`, no I-cache sync |
| Exceptions | vector table, `ESR`/`FAR`, `Except.cool` | IDT with 256 stubs, IST stacks for #DF/NMI, error code and `CR2`, into the same `Except.cool` frame printer and backtrace (frame pointers) |
| Paging | 16 KiB pages, identity map, W^X for kernel text | 4 KiB/2 MiB pages, identity map, `CR0.WP` and NX for the same protections (the "kernel text write" test, heap guard pages); `PAGE_SIZE` becomes an arch constant |
| Context switch | `ArchCtxSwitch` (callee-saved, SP, FP/SIMD) | `rbx rbp r12-r15 rsp`, FPU/SSE state with `fxsave`/`xsave` per task (HolyC F64 lives in SSE) |
| Per-core data (`Fs`, `Gs`) | reserved register `x28` | the GS base MSR, `mov rax, gs:[0]` (x86 has too few registers to reserve one); the coolc x86 target must use the same convention |
| Interrupt controller, IPIs | AIC (M1), GIC (`virt`) | local APIC (x2APIC under KVM/QEMU, xAPIC fallback) and the I/O APIC; IPIs through the ICR |
| Timer | generic timer (`CNTVCT`) | TSC as the counter (invariant TSC required), LAPIC timer in TSC-deadline mode for the tick; TSC frequency from CPUID 0x15/0x16, else calibrated once against the PIT |
| SMP | spin table / PSCI | INIT-SIPI-SIPI with a 4 KiB real-mode trampoline below 1 MiB that reaches long mode with the BSP's page tables |
| Serial | Apple UART, PL011 | 16550 (COM1, port `0x3F8`), polled like today, IRQ 4 later |
| Virtio | virtio-mmio v2 | virtio-pci (modern, 1.0: common/notify/ISR/device capabilities); legacy virtio-pci not supported |
| Clock | coolvm `/chosen`, SMC later | CMOS RTC (ports `0x70`/`0x71`) |
| Power | coolvm finisher, SMC later | ACPI reset register / `0xCF9`, PM1a S5; `isa-debug-exit` in tests |

Virtio: today `Blk.cool` and `NetDrv.cool` each speak virtio-mmio directly. Split them into a
transport (`VirtioMmio`, `VirtioPci`: feature negotiation, status, queue setup, notify, device
config) and the device logic (queues and requests), which stays shared. The drivers are
polled, so interrupts (MSI-X) are not needed at first.

Sources: arch-specific files get an `A64`/`X64` suffix and `Kernel.cool` includes one set
by `#ifdef` on a target define that coolc predefines. `ArchA.coolh` splits the same way.
The arm64 Image must stay byte-for-byte identical through the split (`reloc-check`,
`kernel-rebuild-test` and the seed checks catch any change).

## 4. The boot framebuffer

`Fb.cool` needs a linear framebuffer: address, width, height, stride, pixel format. Sources:
- **UEFI GOP**, filled into `CBootInfo` by the UEFI loader before `ExitBootServices`: real
  PCs, and QEMU with OVMF.
- For the PVH path, which has no firmware: options (a) QEMU's Bochs display (`-device
  bochs-display` or `-vga std`): the framebuffer is PCI BAR 0, the mode is set through the
  Bochs VBE registers, about 60 lines; (b) `ramfb` through fw_cfg; (c) virtio-gpu (a real
  driver, much more). **Rec.: (a)** for development, GOP for everything else.

Input on x86: the serial line first (as today's UART input); then virtio-input (keyboard,
tablet) under QEMU and the i8042 PS/2 controller for real PCs; USB HID is out of scope.

## 5. The kernel image and linking

The module (the HolyC kernel, `Kernel.BIN` from coolc) and the assembly are linked the same
way as on arm64: binlink (`tools/binlink.py`, and `KLink.cool` in the OS) places the module,
writes the relocation table of absolute U64s that `Boot*.S` applies at load time, the kernel
symbol table and the blobs. Changes:

- **Toolchain**: `x86_64-elf-gcc`/`binutils` (Homebrew) for the assembly; clang + lld-link
  for the UEFI loader (as `boot/uefi-probe`).
- **Code fixups**: the x86 backend's BIN has its own import/fixup kinds (rel32 calls into
  assembly routines, imm64 absolutes). binlink and `KLink` get an x86 table of them; rel32
  requires the module within ±2 GiB of the assembly, which the layout guarantees.
- **Assembly relocations** for `BootStub.BIN` and `MakeKernel`'s `StubReloc`: `R_X86_64_PC32`,
  `R_X86_64_PLT32` and `R_X86_64_64`. The assembly is written RIP-relative, so, as on arm64,
  `reloc-check` can require that nothing absolute is left outside the relocation table.
- **The image**: the core stays a flat image with a small header (like the arm64 Image),
  linked at 2 MiB and relocatable to any 2 MiB-aligned address. The PVH `kernel.elf` is that
  image with an ELF header and the PVH note in front (a few hundred bytes, which `MakeKernel`
  can write as well). The UEFI loader is a separate prebuilt `BOOTX64.EFI` that loads
  `\coolcom\kernel.img` from the ESP, so it never has to be rebuilt in the OS.

## 6. Self-hosting on x86

On arm64 the OS compiles its own compiler (`Cmp("C:/Cool/Compiler/Native.cool")` reproduces the
seed) and its own kernel (`MakeKernel` reproduces `kernel.Image`), and the shell JIT-compiles
every line. On x86 the same, with an x86 compiler:

- **The x86 compiler binary.** The kernel embeds a compiler BIN (`Blob.S`), which on x86 must
  be x86 code. The Mac's `build/coolc` cannot run x86 code, so it cannot check an x86 seed's
  fixed point the way `make seed` checks the arm64 one. Options: (a) build it at `make` time by
  cross-compiling the compiler sources with the arm64 seed and `--target x86_64`, and check
  the fixed point inside the x86 OS (`Cmp` there must reproduce it byte for byte); (b) commit a
  second seed, `coolc/seed/Compiler-x86_64.BIN`. **Rec.: (a)**: no second binary in git, and
  the check is stronger: it proves that cross-compiling and native compiling give identical
  output. It relies on coolc's output not depending on the host it runs on, which the
  check itself verifies.
- **The JIT** needs nothing arch-specific beyond the backend: x86 has no I-cache sync, and
  the identity map is writable and executable for JIT pages as today.
- **MakeKernel** takes an x86 `BootStub.BIN` (the prebuilt assembly, made by the host), the
  x86 fixup table in `KLink`, and writes `kernel.elf`. `kernel-rebuild-test` runs unchanged on
  QEMU.
- **Reboot(image)**: there is no coolvm finisher that boots a file. Options: (a) an in-kernel
  handoff: stop the other cores, copy the new image to its load address, jump to its 64-bit
  entry with the same boot info (works under QEMU and on real PCs, like kexec); (b) write it
  to the ESP and reset. **Rec.: (a)**.

## 7. Tests

- `make x86-test` (part of `make test` once it passes): `qemu-system-x86_64 -M q35 -m 1G -smp 2
  -kernel build/x86/kernel.elf -nographic -device isa-debug-exit ...`, TCG on the Mac and KVM
  where available, running the same `DevTest` as `kernel-test` (the parts the milestone
  supports), with the exit code from `isa-debug-exit`. Disks and the network use the same
  images and QEMU's user network with `hostfwd` (as coolvm's `--net-forward`).
- Then the x86 versions of `selfhost-test` and `kernel-rebuild-test`, and a screenshot
  check through QEMU's monitor (`screendump`) for the screen milestone.
- The arm64 suite stays as is and must keep passing unchanged: the arch split is not allowed
  to change the arm64 Image.
- TCG on an M1 is roughly an order of magnitude slower than native, so the x86 tests get
  longer timeouts; CI on a Linux host with KVM runs them at full speed.

## 8. Milestones

1. **Serial shell** (depends on: `coolc --target x86_64`, the arch split). PVH boot, long
   mode, relocation, IDT and exceptions with backtraces, paging and protections, TSC and the
   LAPIC timer, one core, the scheduler, 16550 console, the shell with the JIT and the x86
   compiler in RAM (no disk). Check: `x86-test` sees the shell run a line and `KTest` pass.
2. **SMP** (depends on: 1, the MADT). INIT-SIPI bring-up, per-core GS data, IPIs, the
   scheduler on all cores. Check: `DevTest`'s core and IPI parts.
3. **Virtio-pci disk and network, self-hosting** (depends on: 2, PCI, the virtio transport
   split). C: over virtio-blk-pci, the network over virtio-net-pci, ACPI power-off. Check:
   the file-system and network parts of `DevTest`, x86 `selfhost-test` (the fixed point of
   the x86 compiler) and `kernel-rebuild-test`.
4. **Screen and input, real PCs** (depends on: 3). The UEFI loader with GOP, the Bochs
   display for PVH, virtio-input and PS/2 keyboards, the framebuffer console, Tmux and Vim on
   the screen; a checklist for a first real PC.

## Decisions for you

1. Boot protocol: **PVH for development, then a UEFI loader**; Multiboot2; or the Linux boot
   protocol.
2. ACPI: **tables only, `\_S5` found by scanning the DSDT**; or an AML interpreter.
3. The x86 compiler seed: **cross-compiled at build time, fixed point checked in the OS**; or
   a committed second seed.
4. Per-core data: **GS base**; or a reserved register as on arm64 (costs one of 16).
5. Timer: **TSC + LAPIC TSC-deadline, frequency from CPUID or PIT calibration**; or HPET/PIT.
6. Virtio-pci: **modern (1.0) only**; or legacy too (for old hypervisors).
7. Framebuffer without UEFI: **Bochs display**; `ramfb`; or virtio-gpu.
8. `Reboot(image)`: **in-kernel handoff**; or write to the ESP and reset.

**Decided (user, 2026-09-30):** boot is **UEFI only from the start** (a `BOOTX64.EFI`
PE/COFF image on a FAT ESP, also under QEMU with OVMF; no PVH path), so the screen is
UEFI GOP and the Bochs display driver is not needed. The other decisions follow the
recommendations: ACPI tables only (`\_S5` by DSDT scan), the x86 compiler cross-compiled at
build time with the fixed point checked in the OS, per-core data at the GS base, TSC +
LAPIC TSC-deadline, modern (1.0) virtio-pci only, and `Reboot(image)` as an in-kernel
handoff. x86-64 code that doesn't need privileged instructions (codegen tests, the compiler
fixed point) is tested on the Mac through an x86_64 build of the host runner under Rosetta 2.
