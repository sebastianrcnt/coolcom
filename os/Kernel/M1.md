# M1 kernel port

The hardware contract and its source references are in [docs/m1-platform.md](../../docs/m1-platform.md). This file records the kernel implementation and hardware checks still needed.

## Build and boot decisions

- `make` uses the checked-in native coolc seed to compile `build/Kernel.BIN`, then produces `build/kernel.Image`: an arm64 Image with a 64-byte header, `ARM\x64` at byte 0x38, 16 KiB page flag, and `image_size` covering the kernel's BSS and boot stacks. The link base is DRAM + 2 MiB (`0x800200000`); the HolyC module starts at DRAM + 4 MiB (`0x800400000`). The linker uses two passes.
- m1n1 can load at a different 2 MiB-aligned address, so the Image relocates itself exactly, from a table, not by scanning. `tools/binlink.py` records every place the HolyC module holds an absolute address: `IET_ABS_ADDR` offsets, `DATA_HEAP`/`ZEROED_DATA_HEAP` references, the main table entries, and `IET_IMM_I64` imports of addresses (plain-number IMM exports are not addresses and are skipped; an address in a narrower IMM field, an unaligned site or a doubly patched site is a build error). The list is stored in the module as `RELOC_TABLE` (`U64` link-time module base, `U32` count, `U32` pad, then `U32` byte offsets from the module start; 558 sites today). Before touching global data, the primary core in `Boot.S` compares the link-time module base with the real one (`adrp`) and adds the delta to each listed `U64` (MMU off, so 8-byte aligned), cleans and invalidates each patched line with `dc civac` (the MMU-off stores bypass the caches, so a stale cached copy must not survive), then invalidates the I-cache. The assembly (`Boot.S`, `Arch.S`) is position independent: addresses are taken with the `LA` macro (`os/Kernel/Asm.h`, `adrp`+`add`), never `ldr xN, =sym` or `.quad sym`; the pc-relative code is correct at any base, even when the target is a linker-absolute symbol such as `HC_*`.
- `make reloc-check` (part of `make test`) proves the table is complete. `tools/reloc-check.py --elf` fails on any absolute relocation (`R_AARCH64_ABS64/32/16`, `MOVW_UABS`) in the ELF linked with `-q`, i.e. in the assembly. `--compare` links a second Image 4 MiB higher (`IMAGE_BASE=0x800600000`, same HolyC BIN) and requires the two Images to differ exactly at the table sites (and the table header), each by exactly the base delta. This also catches a stray absolute value in initialized data or a missed patch kind. Both checks were confirmed to fail when an `ldr =sym` is added or a site is dropped. `make test` boots the Image at its link address and again with `coolvm --load-offset 0x600000` (4 MiB higher). The alternate Image also passes when loaded 4 MiB and 2 MiB below and 4 MiB above its link base (negative and positive deltas), and a shifted boot with the table emptied fails, so the relocation is exercised.
- Both primary and secondary entries test `CurrentEL`. The real m1n1 EL2 handoff clears VHE and interrupt routing, then enters EL1h. coolvm starts at EL1h. The real EL2 path has not been exercised on an M1.
- Early MMU tables use 16 KiB granules and 32 MiB level-2 blocks. SoC `0x2_xxxx_xxxx` and the VM finisher region are Device-nGnRnE; DRAM `0x8_0000_0000..0xc_0000_0000` is Normal WB. The tables start at level 2 for `T0SZ=28` (36-bit VA). They cover the full DRAM aperture so the bootloader's chosen Image and DTB positions remain accessible. The allocator uses only FDT `/memory`, skips `/memreserve/` and `/reserved-memory`, and begins after both the Image and DTB.
- `Fdt.HC` reads every 64-bit property as two aligned big-endian 32-bit cells. It obtains RAM ranges, UART/AIC and VM finisher addresses, CPU MPIDRs and release words. The boot console is polled Apple S5L UART; AIC handles peripheral IRQs. CNTV ticks and fast IPIs use FIQ. The FIQ dispatcher reads `IPI_SR_EL1` first, as coolvm requires. SMP writes the FDT release word, cleans it with `dc civac`, and sends `sev`.
- `make run` boots coolvm under a timeout. `make test` boots 2 CPUs with 1 GiB RAM and uses the coolvm finisher exit status. The test requires heap self-tests, scheduler tasks on two cores, timer progress, a fast IPI acknowledgement, and the device tests below. `tools/kernel-test.sh` runs it headless with a fresh 64 KiB disk, a 40 MiB FAT32 disk made by `newfs_msdos` and `mcopy` (mtools), a scripted input queue and a 640x480 framebuffer, then `tools/kernel-verify.py` checks the screenshot pixels and both disk files on the host. `make test` boots twice (link address and `--load-offset 0x600000`).

## Devices and drivers

| Driver | File | Where it works | Discovered from |
|---|---|---|---|
| Console registry (`ConsAdd`, `ConsPut`); `Print`, `PutChars` and input echo go to every output | `Console.HC` | everywhere | n/a |
| Apple S5L UART (polled TX) | `Uart.HC` | M1-real and VM | `serial@` node |
| AIC v1 IRQ/FIQ/IPI | `Aic.HC` | M1-real and VM | `interrupt-controller@` node |
| Framebuffer text console, TempleOS 8x8 font, scrolling | `Fb.HC`, `Font8x8.HC` | M1-real (m1n1 `simple-framebuffer` in `/chosen`) and VM | `simple-framebuffer` compatible |
| Input FIFO: keyboard and mouse | `Input.HC` | **VM-only** (`coolcom,coolvm-input`); real M1 needs USB HID or SPI keyboard drivers behind the same interface | `coolcom,coolvm-input` compatible, IRQ from `interrupts` |
| virtio-blk (virtio-mmio v2, polled) | `Blk.HC` | **VM-only**; real M1 storage is ANS NVMe behind DART | every `virtio,mmio` node, device ID 2 |
| FAT32 file system (TempleOS port) | `Dsk*.HC`, `FileSysFAT.HC` | on any block device | FAT32 boot sector or MBR partition at boot (`DskInit`) |

Nothing is hard-coded: `Fdt.HC` records the framebuffer (`reg`, `width`, `height`, `stride`, `format`), the input node and up to four virtio-mmio nodes by their `compatible` strings.

- **Framebuffer.** The buffer is outside `/memory` and reserved (`no-map`), but on real hardware it sits inside the DRAM aperture that the boot tables map as Normal write-back in 32 MiB blocks. `FbMapNC` splits the affected blocks into 16 KiB pages (a new level-3 table from the heap, installed in the boot level-2 table) and marks only the framebuffer pages Normal non-cacheable (MAIR attr 2), then flushes the TLB. This runs on the boot core before `MPStart`. The block descriptor is replaced by a table descriptor without break-before-make. This is fine while the 32 MiB block is not the one holding the running stack and heap; if a real map puts the framebuffer in the block with the kernel, do the split from the boot code before the MMU is enabled. Pixels are `x8r8g8b8`; other formats leave the console off. `\n \r \b \t` are handled, wrapping is lazy, and scrolling copies the framebuffer up (reads from non-cacheable memory are slow on real hardware; keep a shadow copy if that matters).
- **Input.** `InputIrq` (AIC IRQ from the FDT, delivered to core 0 via `TARGET_CPU`) drains the FIFO. Linux key codes become TempleOS-style messages: an ASCII code (US layout, Shift, Caps Lock and Ctrl-letter handled) and a PS/2 set 1 scan code with the E0 prefix in `SCF_E0_PREFIX` and modifier flags `SCF_SHIFT/CTRL/ALT/CAPS/NUM/SCROLL`, queued in a 256-entry buffer. `GetKey`, `GetChar` and `GetStr(buf, size)` block (yield and wait for interrupt) and echo through the console; `GetStr` edits with Backspace. Mouse state (`mouse.mx/my` clamped to the screen, `wheel`, `buttons`) is a plain struct. `IrqSet` now sets `TARGET_CPU` to core 0; it wrote 0 before, which routes nowhere.
- **Block.** `BlkCount`, `BlkSectors(dev)`, `BlkRead(dev, lba, cnt, buf)`, `BlkWrite`, `BlkFlush` (512-byte sectors, 0 or a negative `BLK_ERR_*`). The driver negotiates `VERSION_1` and `FLUSH`, uses one 8-entry split queue with the header, data and status descriptors, publishes with `dsb sy` before the doorbell and after seeing the used index, suppresses interrupts and polls with a 2 s timeout under a per-device lock. Buffers are addressed by their identity-mapped address. The model is cache-coherent; a non-coherent DMA device would need cache maintenance on the buffers.
- **FAT32.** TempleOS's FAT32 code and the disk layer under it (drives, block devices, block cache, clusters, directories, `FileRead`/`FileWrite`/`Cd`/`Dir`/`DirMk`) are ported from Aiwnios commit e155e87 (`vendor/aiwnios`, gitignored); RedSea, ATA, CD/DVD, ISO files, RAM disks, compression and the DolDoc output are left out. The bottom calls `BlkRead`/`BlkWrite` of `Blk.HC` (TempleOS's drive-level `BlkRead`/`BlkWrite` are `DrvBlkRead`/`DrvBlkWrite` here). `DskInit` makes every FAT32 volume a drive, `C:` first, from a bare FAT32 boot sector or MBR partitions; each task has a current drive and directory (`CTask.cur_dv/cur_dir`) and starts on the first drive at `/`. There are no exceptions in the kernel yet, so failures print `ERROR:` and return; names compare case-insensitively and long names up to 26 characters are read and written; dates are a fixed 2026-01-01 as there is no clock; short names of long names are not made unique. The file headers list the other changes from TempleOS. `DskCopy.HC` adds `Del`, `Copy`, `Move`, `IsDir` (TempleOS) and `Type` (plain text), `MkDir` and `Rename` (aliases). `FileRead`, `FileWrite`, `Cd`, `Dir`, `DirMk`/`MkDir`, `Del`, `Copy`, `Move`/`Rename` and `Type` are in the shell (`ShellA.HH`).
- **Tests** (`DevTest.HC`, only with `coolcom.test=1`): the scripted keys and mouse events must produce the line `hiA` and the expected mouse state; sector reads, range errors, a two-sector write, flush and read-back must work and the host checks every sector of the disk file; on the FAT32 disk the kernel reads the host's `HostNote.txt`, writes `FromCoolcom.txt` twice (3000 bytes the second time), makes `Sub` and writes `Sub/Inner.TXT`, lists the root and reads everything back, and afterwards mtools must read the same files on the host and `fsck_msdos -n` must find the volume clean; the kernel finally clears the screen and draws four text rows, colour bars and a ramp, which the host compares pixel for pixel against the font.
- **Exception red zone.** The Aiwnios code generator saves callee-saved registers *below* `sp` (`stp x19, x20, [sp, #-16]`, then `sub sp`) and restores them the same way. An interrupt landing between those instructions overwrote them with the exception frame, which showed up as a rare (about 1 in 8) crash in `DevTestBlk` once more code ran between interrupts. `Arch.S` now reserves a 512-byte red zone (`REDZONE`) under the interrupted `sp` before it builds the frame.
- **HolyC stage-0 pitfalls found on the way:** a `$` in a comment broke parsing, and the error was reported at a later `#include` (bisect by truncating at function boundaries).

## TempleOS header and library

- **Header.** `KernelA.HH` is TempleOS's (Aiwnios e155e87, via the compiler's copy `coolc/Frontend/KernelA.HH`), generated by `tools/mkkernela.py`: all its classes and `#define`s and its `extern` prototypes, without the Aiwnios host `import`s and without the classes the kernel lays out itself (`CCPU` in `MultiCore.HC`, the heap's `CHeapCtrl`/`CMemBlk` in `Mem.HC`). Tasks are TempleOS `CTask`s (`Sched.HC`: `next_task`/`last_task` are the core's ring, `task_flags` uses the `TASKf_*` bits, `context_save_area[0]` holds the switched-out stack pointer); `Bool` is TempleOS's `U64`. A kernel definition may differ from its TempleOS prototype (the compiler warns "Fun header ... mismatch"); calls compiled before the definition use the prototype.
- **Library.** Strings, printing, math, hash tables, queues, defines and scanning are TempleOS's code, the same files the compiler is built from (`coolc/Runtime`: `KGlbls`, `KMisc`, `CQue`, `KDataTypes`, `StrA`, `KHashA/B`, `KMath`, `KMathB`, `StrPrint`, `StrB`, `KDefine`, `StrScan`, `QSort`, `NativeExcept` for try/catch/throw). `#define COOLCOM_KERNEL` leaves out, there, what the kernel does its own way (`Sleep`, `SleepUntil`, `IsSilent`). The kernel supplies what Aiwnios's C host does: `KUtils.HC` (memory and string primitives, bit operations, `IsValidPtr`), `KPrint.HC` (`PutS`, where `Print` ends, and `RawPrint`, which formats without the heap for the heap and exception handlers), `KHost.HC` (ticks, `NativeExit` for an uncaught `throw`, stand-ins for DolDoc, pop-ups and sound), `KMathC.HC` (`Exp`, `Ln`, `Pow`, `Sin`, `ATan`, ...; `Sqrt`, `Floor`, `Ceil`, `Round` are instructions in `Arch.S`). From Aiwnios `Src`: `KDate.HC` (dates; `Now` is the host's clock, which coolvm puts in `/chosen` as `coolcom,unix-time` and `coolcom,utc-offset`; a real M1 starts at 1970 until the SMC RTC is read) and, in `Sched.HC`, `TaskValidate`, `Kill`, `Suspend`. `tools/mkprelude.py` fails the build if the kernel and the library define the same function (HolyC would keep the later one without a word).

## Shell

`Shell.HC` is a TempleOS-style command line: each line read with `GetStr` is JIT-compiled by the Cool compiler and run at once, and functions and globals persist from line to line (they live in the compiler task's hash table).

- **Compiler.** The checked-in seed `coolc/seed/Compiler.BIN` is embedded in the Image by `Blob.S` (`.incbin`, in the boot stub's read-only data below `MODULE_BASE`; about 570 KiB of room is left, the linker `ASSERT` catches an overflow) and loaded at run time by `BinLoad.HC`, a HolyC port of the loader in `coolc/Host/native.c`: the file is copied to the heap, exports, absolute addresses, data heaps and imports are patched, the I-cache is synced and the 2000-odd initializers run. Imports resolve against a table of kernel routines first (`ShellRtInit`: the services `native.c` provides, e.g. `NativeJitAlloc`/`NativeJitCommit`, `MAlloc`, `Fs`/`SetFs`, `AIWNIOS_SetJmp`/`LongJmp`), then the module's exports; an import nothing defines gets a stub that prints its name and halts the task when called.
- **JIT.** The shell calls the compiler's `ExePutS`, which calls back `ExeCmdLine` (the compiler imports it; the kernel's `ShellExeCmdLine` loops `LexStmt2Bin` + call, like TempleOS). Function code goes to heap memory (identity mapped RWX) through `NativeJitCommit`, which copies it and runs `ArchICacheSync` (`dc cvau`, `dsb ish`, `ic ivau`, `dsb ish`, `isb`). Statement code is not freed, since a global may point at a string constant inside it.
- **Kernel symbols.** `tools/binlink.py` appends a symbol table to the module (`KSYM_TABLE`: every HolyC export and assembly symbol, sorted by address, stored relative to the table so it needs no relocation; `KSym.HC`). Before the first line the shell adds every entry as a `HTT_EXPORT_SYS_SYM` hash entry (`ShellSyms`) and compiles a prelude, `build/ShellPrelude.HH` (embedded by `Blob.S`), which `tools/mkprelude.py` makes from the kernel sources in include order: their `#define`s, classes and unions, an `extern` prototype for every function (assembly `import`s included) and an `extern` for every global variable. In JIT mode `extern` binds each one to the system symbol of that name, so shell code uses any kernel function or global directly; nothing is listed by hand. The prelude (about 150 KB) is stored in the kernel module by `binlink.py` (`SHELL_PRELUDE`); an error in it stops the rest, so the shell would lack everything after it. `FunSegFind`/`StrPrintFunSeg` turn a code address into function+offset from the same table; a fault in shell code reports where it happened that way (`code at StrLen+0x34`); for a function compiled in the shell it looks through the compiler's hash table (`code at F+0x14`).
- **Constraints.** Compiler-built code reads `Fs` as `[x28]`; the shell task points x28 at `shell_tls` (`ArchX28Set`), kernel HolyC never uses x28 and task switches save it, so only the shell task may run the compiler. The shell reaches into the compiler's `CCmpCtrl` (token, flags, htc hash tables) and `CHashExport` at fixed offsets taken from `coolc/Frontend/KernelA.HH`; `ShellExeCmdLine` checks the hash-table fields and refuses to run if they don't match. The shell task has a 2 MiB stack (`Spawn` takes a stack size now). The compiler's file imports (`FileRead`, `FileWrite`, `FileNameAbs`, `ExtDft`, `ExtChg`) use the FAT32 drives, so `#include "Test.HC"` reads `C:/Test.HC` (relative to the shell's current directory); a call to an import nothing defines prints `ERROR: unresolved import ...` and goes back to the prompt (the statement, or the whole line if it happened while compiling), and a fault in shell code halts the system like any kernel fault.
- **Test.** After the `hiA` line the input script types `I64 Sq(I64 x) { return x * x; }` and `Print("%d\n", Sq(7));` (generated by `tools/kernel-verify.py`); `DevTestShell` runs the shell for two lines and then evaluates `Sq(7);` itself, which must return 49, and `tools/kernel-test.sh` requires a line `49` in the output. Without `coolcom.test=1` the kernel starts the shell on core 0 after the demo and it reads lines forever.
- The US key map lacked `%`, so Shift+5 through Shift+- gave the symbol of the next key and Shift+= gave nothing; fixed in `KbdMapInit`.

## M1 hardware checks

1. Boot the Image with the unmodified Asahi `t8103-j274.dtb` through m1n1 `linux.py` or as a last payload. Verify the image relocation and FDT memory reservations against a real 8 or 16 GiB memory map.
2. Verify that dropping from m1n1's VHE EL2 state to EL1 delivers CNTV FIQs directly. If `HCR_EL2.FMO` or `VM_TMR_FIQ_ENA_EL2` needs different setup, adjust the EL2 handoff. coolvm cannot validate this path.
3. Check `ID_AA64MMFR0_EL1` for 16 KiB page support, and verify page-table attributes with the actual Apple bus. The current broad DRAM mapping includes carve-outs as Normal, although the allocator never touches them; refine mappings from the FDT before using framebuffer or DMA devices.
4. Confirm UART0 availability and baud after m1n1 shuts down USB. A physical VDM serial cable or m1n1 HV guest is needed for console output on a Mac mini.
5. Confirm m1n1's CPU release words and cache maintenance on both Icestorm and Firestorm cores. The coolvm test exercises only E0 and E1.
6. The real SMC power-off protocol is not implemented. The finisher is selected only when FDT root compatibility starts with `coolcom,coolvm`.
7. The framebuffer console assumes m1n1's `simple-framebuffer` (x8r8g8b8 from `/chosen`) and the non-cacheable remap above; verify on hardware that the remap works and scrolling speed is acceptable. Keyboard and storage need real drivers (USB HID via the DWC3/Type-C stack or the SPI keyboard, and ANS NVMe with DART); the VM-only input and virtio-blk drivers are not present on an M1.
